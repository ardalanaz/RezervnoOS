## قدم‌های بعدی (ترتیبِ درستِ ایمن)

### قدم ۳ — e2e رفتاریِ عمیقِ پنل‌ها (پیش‌نیازِ هر ادغامِ پرریسک)
**چرا اول این:** اسموکِ فعلی فقط «لود شدن» را چک می‌کند. برای refactorِ ایمنِ API client
(که auth/session دارد) به تستِ **رفتاری** نیاز است.
- ورودِ staff (mockِ `/auth/staff/*`) + یک-دو فلوِ کلیدیِ هر پنل (لیستِ رزرو business، لیستِ رستوران‌های company) با mockِ API.
- الگو: همان `helpers/mock-api.ts` و `actions.ts`ِ customer، برای سطحِ panel.
- **ریسک:** کم (فقط تست). **ارزش:** بالا (شبکهٔ ایمنیِ واقعی).

### قدم ۴ — ادغامِ API client (تدریجی، پس از قدم ۳)
سه client متفاوت‌اند (customer: refresh/session کامل؛ business `data.js`؛ company `api.js`).
- **۴آ) هسته‌ی transport مشترک** (base/timeout/envelope/offline) → `shared/js/` + codegen. کم‌ریسک.
- **۴ب) لایه‌ی auth/refresh** فقط پس از پوششِ e2eِ قدم ۳؛ با byte-identity هرجا ممکن.
- **ریسک بدونِ قدم ۳:** بالا (رگرسیونِ نشست دیده نمی‌شود) → **عمداً به تعویق افتاد**.

### قدم ۵ — ادغامِ API client (انجام‌شد)
- **۵-الف:** هسته‌ی transport مشترک `shared/js/api-core.js` (`httpJson`) + customer روی آن. — PR #54.
- **۵-ب:** پنل‌ها (business/company) روی همان `httpJson` نسخه‌ی global. — PR #55.

### قدم ۶ — منطقِ مشترکِ پنل‌ها (بازبینیِ صادقانه)
**یافته:** برخلافِ فرضِ اولیه، view‌های `overview/waitlist/loyalty/chat` بینِ دو پنل
**تکراری نیستند** — دامنه‌شان فرق دارد (business = پنلِ رستوران؛ company = پنلِ پلتفرم).
`company` اصلاً `waitlist/loyalty/chat` ندارد و دو `overview.js` واقعاً view‌های متفاوت‌اند.
ادغامِ اجباریِ آن‌ها ضدِّالگوست (همان درسِ icons.js).
- **تکرارِ واقعیِ باقی‌مانده:** فقط helperهای خالص. `fa` و `esc` در دو پنل byte-identical
  بودند → تک‌منبع در `shared/js/format.js` (نسخه‌ی global). — PR #56.
- **عمداً یکی نشد:** `fa`ِ customer معنایِ متفاوتی دارد (تبدیلِ رقم، نه فرمتِ عدد)؛
  `toast`ِ دو پنل هم متفاوت است (business انیمیشن/a11y دارد).
